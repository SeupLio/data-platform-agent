# 数据平台 Agent · 评测体系设计

> 这份文档回答一个问题：**凭什么说这个 Agent 好用？**
> 以及一个更重要的问题：**凭什么相信这个评测本身没在骗人？**

---

## 1. 为什么要自建评测

「跑几个 case 看看」的做法有三个致命的坑，本项目的评测设计就是为了绕开它们：

| 坑 | 表现 | 本项目的对策 |
|---|---|---|
| **期望值复用被测代码** | 用被测函数算期望值 → 实现错了，期望值跟着错 → **恒绿而什么都没测到** | 期望值由独立 Oracle 计算（自写 SQL + 自写口径解析），时间区间期望是**手写死值** |
| **指标结构上看不见改动** | 真实效应被稀释到 0，却不报错 | 每个变异体必须让**至少一维掉分**，且掉在**预期的那一维**上 |
| **一条永远绿的断言** | 满分没有信息量 | 断言「每一维在用例上都不是恒 1」；变异测试作为评测的「牙齿」 |

## 2. 五个维度

定义在 `src/dataagent/eval/metrics.py`，权重 `WEIGHTS = {accuracy: 0.35, reasoning: 0.25, adaptation: 0.20, efficiency: 0.10, experience: 0.10}`。

| 维度 | 回答的问题 | 判分方式 |
|---|---|---|
| `accuracy` 问答准确率 | 指标选对了吗？数和 Oracle 一致吗？治理规则召回了多少、误报了多少？ | 问答类 = `0.5×指标正确 + 0.5×数值一致`；治理类 = 规则集合的 **F1**；反问/拒绝类 = 行为是否命中 |
| `reasoning` 数据推理有效性 | SQL 真的用了这个口径要求的字段吗？归因主因找对了吗？ | 问答类 = SQL 是否包含指标公式的全部字段且表名正确；分析类 = 主因维度值与维度名是否命中；治理类 = 期望规则**全召回** |
| `adaptation` 场景适配度 | 该答的答了吗？该反问的反问了吗？该拒的拒了吗？维度/筛选按问法来了吗？ | 行为类型匹配 × 结构匹配（筛选与维度不对则 ×0.6） |
| `efficiency` 响应效率 | 在延迟与步数预算内收敛了吗？ | `0.6×延迟分 + 0.4×步数分`，延迟预算 2000 ms |
| `experience` 用户体验 | 有没有带口径、带证据、带可读结论？ | 回答含口径定义 + 证据块非空 + 有数值文本 → 1.0，否则 0.5 |

### 2.1 数值一致性（`_value_ok`）

```python
def _value_ok(actual, expected, tol=1e-6):
    if actual is None or expected is None:
        return False
    if expected == 0:
        return abs(actual) < 1e-9
    return abs(actual - expected) / abs(expected) <= tol
```

**容差 1e-6 是刻意收紧的**：Oracle 与 Agent 走的是两条独立代码路径，
如果口径实现正确，两边算出的和应当逐位一致；容差放宽会把口径错误掩盖成「浮点误差」。

### 2.2 效率分（`_efficiency`）

```python
lat  = 1.0 if ms <= 2000 else max(0.0, 1 - (ms - 2000) / 2000)
step = 1.0 if steps <= budget else max(0.0, 1 - (steps - budget) / budget)
return round(0.6 * lat + 0.4 * step, 4)
```

延迟权重更高，因为**步数超预算会先触发 Agent 的「未收敛」错误**（`kind=error`），
而延迟超预算是用户唯一能直接感知的退化。

## 3. 用例集（143 条）

生成器 `src/dataagent/eval/cases.py::generate_cases()`，产物 `cases/eval_cases.json`，
由 `scripts/gen_cases.py` 生成。**改了生成器必须重跑**，有护栏测试盯着。

| 类型 | 条数 | 在测什么 |
|---|---|---|
| `qa` 基础问答 | 64 | 32 个指标 × 2 种时间说法；指标选择 + 时间解析 + 数值一致性 |
| `qa` 结构化问答 | 8 | 维度（按分区/各端）与筛选（游戏分区/iOS 端）是否正确落到查询计划里 |
| `qa` 指标消歧 | 13 | 歧义问法必须**反问**，且给出 ≥2 个可选口径；不得返回数值 |
| `qa` 安全与边界 | 10 | 越权/敏感/知识库外问法必须**拒绝**，不得返回数值 |
| `insight` 自动分析 | 20 | 归因主因命中（4 条有标准答案）+ 基期对齐 + 结论生成 |
| `govern_sql` 治理-SQL | 21 | 规则集合的召回与精确率（F1），含 5 条合规 SQL 必须 0 误报 |
| `govern_table` 治理-表 | 7 | 表命名规范，含 3 条合规表名必须 0 误报 |

**答案类用例 120 条（83.9%）**，其余 23 条是「不该给答案」的用例 —— 这类用例最容易被忽略，
但它们是「不编数字」这条产品原则唯一的验证手段。

## 4. 期望值的独立性

这是整个评测里最容易做错的地方。

### 4.1 Oracle 不走被测代码路径

`src/dataagent/eval/oracle.py` 自己实现了一套口径解析：

```python
def parse_oracle_expr(formula) -> (kind, numerator, denominator):
    # 自己写正则、自己判断 additive / ratio / distinct
```

再用**裸 SQL** 直接问 sqlite：

```python
SELECT SUM(play_cnt) FROM dws_video_daily WHERE date BETWEEN ? AND ?
```

而被测 Agent 走的是 `MetricExpr` → `compile_sql` → `Warehouse.execute` 这条路径。

**为什么必须分开**：如果 Oracle 复用 `MetricExpr`，那么变异体
`M6-distinct-as-additive`（把去重指标当可加指标）会**同时污染期望值和实际值**，
两边一起错、评测全绿 —— 这正是「评测恒绿」的经典成因。

### 4.2 用 4 条手写 SQL 锚住 Oracle

Oracle 本身也可能错，所以用**人工写死的 SQL** 反向验证它（`ANCHOR_SQL`）：

| 指标 | 锚点 SQL（节选） |
|---|---|
| `play_cnt` | `SELECT SUM(play_cnt) ... WHERE date BETWEEN '2026-09-18' AND '2026-09-24'` |
| `finish_rate` | `SELECT CAST(SUM(finish_cnt) AS REAL) / SUM(play_cnt) ...` |
| `dau` | `SELECT SUM(dau) ... WHERE date BETWEEN '2026-09-14' AND '2026-09-20'` |
| `active_up_cnt` | `SELECT COUNT(DISTINCT up_id) ... WHERE date = '2026-09-24'` |

测试 `tests/test_eval.py::test_oracle_matches_hand_written_sql` 断言两者一致。

### 4.3 时间区间的期望是手写死值

```python
TIME_FIXTURES = (
    ("最近7天", "2026-09-18", "2026-09-24"),
    ("昨天",   "2026-09-23", "2026-09-23"),
    ("上周",   "2026-09-14", "2026-09-20"),
    ("上月",   "2026-08-01", "2026-08-31"),
    ...
)
```

**不用 `nlu.parse_time` 反推期望值** —— 否则时间解析写错了，期望值会跟着错，测试依然全绿。

### 4.4 治理规则号是人工标注的

21 条 SQL 用例的期望规则集合按知识库 `governance_rules.md` 的规则文本人工标注，
不调用 `check_sql` 反推。

## 5. 变异测试：验证评测有牙齿

定义在 `src/dataagent/eval/mutants.py`。每个变异体通过 `contextmanager` 在**运行期**注入缺陷，
跑完整套用例，然后比较五维均值。

| 变异体 | 注入的缺陷 | 结果 | accuracy | reasoning | adaptation | efficiency | experience |
|---|---|---|---|---|---|---|---|
| `M1-no-clarify` | `CLARIFY_RATIO = 0.0`：命中多候选直接选第一个 | **被抓** | −0.462 | −0.462 | −0.462 | 0 | −0.231 |
| `M2-ignore-range` | `nlu.parse_time` 一律返回最近 7 天 | **被抓** | −0.273 | −0.028 | 0 | 0 | 0 |
| `M3-disable-G01` | `check_sql` 过滤掉 G01 | **被抓** | −0.030 | −0.035 | 0 | 0 | 0 |
| `M4-attribution-unsorted` | 归因结果按 \|delta\| **升序**排 | **被抓** | 0 | −0.028 | 0 | 0 | 0 |
| `M5-no-context` | 回答只留数字，去掉口径与证据 | **被抓** | 0 | 0 | 0 | 0 | −0.252 |
| `M6-distinct-as-additive` | 去重指标当成可加指标 | **被抓** | −0.007 | 0 | 0 | 0 | 0 |

**6 / 6 被抓。** 读这张表有三个要点：

1. **看「掉在哪一维」，不只看「有没有掉」。** M4 只掉 `reasoning`，M5 只掉 `experience` ——
   这说明五个维度确实在测五件不同的事，没有串味。
2. **M6 只掉 0.007，但它是真的被抓到了。** 因为只有 2 条用例（活跃UP主数）会受影响。
   幅度小不等于没测到 —— 但也要承认：**这个变异体只被 2 条用例覆盖，样本很薄。**
3. **M3 掉 0.030 同理**，G01 只影响 8 条用例。

> 这三条「薄覆盖」是这份评测的真实弱点，写在 §7 的局限里，不藏。

`tests/test_mutants.py` 把上面每一条都做成了断言，包括：
「每个变异体必须被抓」+「必须掉在预期的那一维上」+「六个都要被覆盖」。

## 6. 怎么跑、怎么迭代

```bash
python -m dataagent.cli eval       # 143 条，写 docs/reports/eval_report.{md,html,json}
python -m dataagent.cli mutate     # 6 个变异体，写 docs/reports/mutation_report.md
python -m dataagent.cli eval --checkpoint runs/ck.jsonl --resume   # 断点续跑
python -m dataagent.cli studio     # 网页自测台，点按钮就能跑一遍
```

**报告是给人做决策的**：先给结论（综合 + 五维），再给证据（分场景、未满分用例明细、
变异测试表），最后给「这份报告没覆盖什么」。

**迭代纪律**：

| 改了什么东西 | 必须做什么 | 哪个护栏会先红 |
|---|---|---|
| 改了用例生成器 | 重跑 `scripts/gen_cases.py` | `test_generated_cases_match_committed_file` |
| 改了原始 wiki 语料 | 重跑 `scripts/build_kb.py` | `test_build_is_deterministic_and_fresh` |
| 新增指标 / 别名 | 检查是否有重复别名、易混对是否可解析 | `test_no_duplicate_alias_across_metrics`、`test_confusable_pairs_are_symmetric_and_resolvable` |
| 新增治理规则 | 加规则文本 + 加用例 + 加反向用例（合规 SQL 必须 0 误报） | `test_mutant_drops_the_dimension_it_should` |
| 新增维度 | 确认该维在用例上有非满分分布 | `test_no_dimension_is_constantly_perfect_or_zero` |

## 7. 这份评测没覆盖什么（诚实清单）

1. **没有真实模型参与。** 规划器是确定性规则，评测的是规则链路，
   不是「大模型规划质量」。LLM 规划器的对照实验**没有做过，因此不给任何数字**。
2. **没有真实用户。** 采纳率、满意度、真实问法分布全都量不到；
   用例里的问法是我设计的，天然偏向「实现能答对」的形态。
3. **「用户体验」是结构化判分**（有没有带口径、带证据、带结论），
   不等于用户主观体验，不能当 NPS 用。
4. **`accuracy = 1.0000` 是回归基线，不是能力上限。** 用例与实现对着长出来，
   真正说明评测有效的是变异测试 6/6，而不是这个满分。
5. **M3 / M6 两个变异体只被个位数用例覆盖**，如果这两处的实现坏了，
   掉分幅度只有 0.007~0.035，**很容易被别处的波动掩盖**。补用例是下一步。
6. **治理规则判的是 SQL 文本特征**（正则 + 函数调用识别），不是真正的 SQL 解析器，
   复杂嵌套 SQL、子查询别名遮蔽会漏判。
7. **没有做统计显著性**：143 条用例全量跑，没有重复采样，也没有给区间。
   单次读数就是单次读数。
8. **数仓是自造的模拟数据**，`insight` 用例的标准答案是**我注入的异常**，
   真实业务里的异常往往没有这么干净的单一主因。
