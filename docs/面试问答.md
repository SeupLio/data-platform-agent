# 数据平台 Agent · 面试问答（面经）

> 配套项目：`data-platform-agent`（本仓库）。所有数字都能在仓库里复现：
> `python -m dataagent.cli selftest` 会把关键数字重算一遍。

## 0. 60 秒自我介绍（项目部分）

> 我做了一个数据平台 Agent 的原型，对应这个岗位的三块职责。
> 第一块是知识库：我把模拟 wiki 的非结构化语料拆成结构化知识，32 个指标、6 张数据模型、
> 10 条治理规范，一共 148 个可独立引用的知识块，并且做了检索和口径消歧 —— 口径分不清时它会反问，
> 不会猜。第二块是三个 Agent：智能问答、自动分析、治理助手，跑在同一套知识库上。
> 第三块是评测：143 条用例、五个维度，期望值由独立 Oracle 计算，不复用被测代码；
> 另外做了 6 个变异体，注入真实退化看评测能不能抓到，结果是 6 比 6 全抓。
> 整个项目离线可复现，不配任何 API Key 就能跑通，测试 99 项全绿。

## 1. 项目总览

**Q1.1 这个项目最难的地方是什么？**
不是调模型，是**让「口径」这件事在系统里只有一个真相**。一开始我把指标定义写在 YAML 里手写维护，
很快就发现同一个口径在三个地方各写一份（知识库、用例、SQL），改一处另外两处不动，谁都不报错。
后来改成「原始 wiki 语料是唯一真相源，产物必须能从语料逐字节重建」，并配了新鲜度护栏，
才把这类问题堵住。**判据是：这件事有几个产出点？多于一个就会在某个未来时刻分家。**

**Q1.2 为什么不用大模型做？**
我把它拆成两层。时间区间、口径选择、维度筛选这些**错了不会有痕迹**的部分，我用确定性规则；
大模型只在「把用户的话改写成规则能认的形式」这一层有意义。
所以我刻意把**规划器和 Agent 循环解耦**：现在挂的是规则规划器，换成 LLM 规划器时，
循环、步数预算、trace、评测都不用动，可以直接做「规则 vs 模型」的对照评测。
但我要说明：**这个对照实验我没有做过，所以我不给任何「模型更好」的数字。**

**Q1.3 这个项目你现在最不满意的地方是什么？**
两个。一是**两个变异体覆盖太薄**：`M6-distinct-as-additive` 只影响 2 条用例，
掉分幅度只有 0.007，如果这处实现坏了，很容易被别处的波动掩盖。
二是**用例的问法是我设计的**，天然偏向「实现能答对」的形态，真实用户的问法分布我量不到。
这两条我都写在评测文档的「没覆盖什么」里，不藏。

## 2. 知识库

**Q2.1 知识库的「知识拆解」具体拆了什么？**
两层拆解。第一层是把非结构化 wiki 的段落拆成结构化字段：一个指标拆出
指标编码、业务域、口径定义、计算方式、来源表、支持维度、单位、数值类型、指标层级、
口径负责人、别名、易混指标、注意事项，共 13 个字段。
第二层是把一个指标再拆成 5 类**可独立引用的原子知识点**（chunk）：定义、公式、维度、
口径注意、易混指标，id 形如 `play_cnt::formula`，一共 148 个。

**Q2.2 为什么回答要引用 chunk 而不是整篇文档？**
因为「证据」必须能指到具体一句。如果回答里只写「依据：播放量口径」，
用户没法验证我读的是定义还是注意事项；写「依据 `play_cnt::formula`」才能对得上，
才能被审计。这也是评测里「用户体验」那一维的判分依据之一。

**Q2.3 拆解的时候你怎么保证不出错？**
关键是在**构建期**把知识库的自相矛盾变成必然失败，而不是等运行期偶发报错。有两条我觉得最有价值：
① 指标引用了未注册的表 → 直接抛异常；② 指标依赖的字段不在来源表的字段清单里 → 直接抛异常。
第二条尤其重要：表和指标可能被不同的人改，各自看都没错，合起来就不一致，
**这种不一致不会自己暴露**，只能靠构建期的交叉校验。
另外计算式解析不出来也直接炸 —— 一个解析不出来的口径，比一个错误的口径更该被发现。

**Q2.4 易混指标是怎么处理的？**
wiki 里易混关系是单向写的（各页面各写各的），但检索必须当**无向**用，
否则「从 B 查 A」会漏掉消歧。所以构建时把它归一化成无向对并去重，现在有 12 对，
比如「播放量 ↔ 播放人数」（计次 vs 去重计人）、「完播率 ↔ 有效播放率」（走到结尾 vs 播放≥30秒）、
「人均播放时长 ↔ 人均使用时长」（分母是播放人数还是 DAU）。

**Q2.5 加一个新指标要动什么？**
在 wiki 语料里加一个块填 13 个字段，跑构建脚本，跑 `kb stats` 看条目数和重复别名，跑测试。
会先红的护栏我列过：忘了重跑构建有新鲜度护栏；编码重复或别名撞车有唯一性护栏；
引用了不存在的表或字段，构建期直接炸。**新增治理规则还要多补一条反向用例**
（合规 SQL 必须 0 误报）—— 只加会红的用例是治理类规则最常见的翻车方式。

## 3. 产品设计

**Q3.1 为什么「反问」是这个产品的核心行为？**
因为在数据问答里，**口径选错比答不上来危险得多**。答不上来用户会换个问法；
口径选错，用户会拿着一个错的数字去开会，而且**没有任何人会发现问题**。
所以我把「分不清就先问一句」做成一等公民行为：命中多个候选且分不开时，
不给数字，列出可选口径让用户选。

**Q3.2 那不会反问太多、体验很差吗？**
会，这是真实风险，我做了两件事。第一是**把子串包含和口径冲突分开**：
「人均播放时长」里含「播放时长」，问得具体不该被反问。
规则是只有两个别名**都出现在问题里**时才消解歧义（取更精确的那个）；
用户只打「播放」这种片段时两个口径是真分不开，必须反问。
第二是阈值可配（现在 0.80），后续可以把高频歧义问法沉淀成「推荐口径」，
同一用户重复问同一口径时记住选择。

**Q3.3 归因为什么不用「哪个维度值最大」当主因？**
因为**最大的维度值可能根本没变化**。归因要看的是变化量，所以我把
`当前值 − 基期值` 拆到每个维度取值上，输出 delta 和贡献占比，按 |delta| 排序。
另外基期是自动取**等长**的前一区间（7 天对 7 天），
避免工作日/周末构成不同造成的伪变化。

**Q3.4 治理助手为什么不做成「给建议」而是「出问题清单」？**
因为治理的交付物必须是**可执行、可派活**的。清单里每条都有规则号、级别（P0/P1/P2）、
命中证据、修复建议、责任组 —— 这样开发能改，治理同学能追踪，而不是「AI 觉得你这段 SQL 不太好」。
规则本身也是**数据驱动**的：10 条规则的文本写在 wiki 里，代码只实现「怎么判」，
加规则改 wiki 不改代码。

**Q3.5 这个产品跟现有的指标平台是什么关系？**
定位是**消费侧入口 + 治理侧前置闸门**，不碰口径定义。
口径的权威源仍然是指标平台，我这个知识库是它的消费侧缓存。
我在产品方案里明确写了「不做新的指标平台」，因为那会制造第二份口径真相源，
正好是我们要解决的问题。

## 4. 评测（这个岗位最容易被追问）

**Q4.1 五个维度分别是什么？为什么要这五个？**
问答准确率（指标选对没、数对不对、治理规则的 F1）、数据推理有效性（SQL 有没有用这个口径要求的字段、
归因主因找对没）、场景适配度（该答/该反问/该拒有没有做对，维度筛选有没有按问法来）、
响应效率（延迟和步数预算）、用户体验（有没有带口径、带证据、带结论）。
这五维对应的是「答得对 / 推得对 / 该不该答 / 答得快 / 答得清楚」五件不同的事。
我有条测试专门断言**没有任何一维在所有用例上恒为 1** —— 一维恒 1 说明它没在测量东西。

**Q4.2 143 条用例是怎么分布的？**
基础问答 64 条（32 个指标 × 2 种时间说法）、结构化问答 8 条（维度/筛选）、
指标消歧 13 条、安全与边界 10 条、自动分析 20 条、治理 SQL 21 条、治理表名 7 条。
其中**「不该给答案」的用例有 23 条**（反问 13 + 拒绝 10），
这类最容易被忽略，但它们是「不编数字」这条产品原则唯一的验证手段。

**Q4.3 期望值是怎么来的？为什么不能直接用被测代码算？**
这是评测里最容易做错的地方。如果 Oracle 复用被测的 `MetricExpr`，
那么「口径解析写错了」会**同时污染期望值和实际值**，两边一起错、评测全绿 —— 这就是评测恒绿的经典成因。
所以 Oracle 自己实现了一套口径解析，用裸 SQL 直接查 sqlite，
跟被测的「编译查询计划 → 执行」完全是两条路径。
另外时间区间的期望值是**手写死值**，不是调时间解析函数反推的。
Oracle 本身也可能错，所以我用 4 条人工写死的 SQL 做锚点反向验证它。

**Q4.4 那你凭什么相信这个评测本身？**
靠**变异测试**。我注入了 6 类真实会发生的退化：去掉口径消歧、时间解析忽略显式区间、
治理漏掉一条规则、归因按升序排（把主因埋掉）、回答只给数字不带口径、去重指标当可加指标。
结果是 **6 个全部被抓**。而且我加了第二条断言：**必须掉在预期的那一维上** ——
M4 只掉 `reasoning`、M5 只掉 `experience`，说明五个维度确实在测五件不同的事，没有串味。
掉在不相干的维度上说明维度定义串味了，这也要报错。

**Q4.5 基线是 1.0000，这是不是说这个产品已经很好了？**
不是，我在 README 和评测文档里都明确写了：**满分是回归基线，不是能力上限。**
用例和实现是「对着长」出来的，一个只会给满分的评测体系等于没有评测。
真正说明评测有效的是变异测试 6/6，而不是这个 1.0000。
如果要对外汇报，我会拿变异测试和「该拒绝的有没有拒绝」这类用例说事，不会拿满分说事。

**Q4.6 评测怎么迭代？**
我把「改了什么 → 必须做什么 → 哪条护栏会先红」做成了表。
改了用例生成器必须重跑生成脚本（有用例集一致性护栏）；
改了 wiki 语料必须重跑构建（有产物新鲜度护栏）；
新增维度要确认该维在用例上有非满分分布；新增治理规则要同时补反向用例。
原则是：**靠人记得的约定迟早会漏，要么变成默认值，要么配一条会红的护栏。**

**Q4.7 如果让你把这个评测用在真实业务上，第一步做什么？**
先补「真实问法分布」。现在用例的问法是我设计的，偏向实现能答对的形态。
我会先收集 1~2 周的真实提问日志，按问法聚类，算出高频问法 Top 50 的覆盖率，
再把这些问法补进用例集 —— 否则评测在测一个不存在的用户。
第二步是给口径正确性找权威源：现在没有指标平台可对账，
真实环境里应该把「回答的口径 == 指标平台的口径」做成一条硬断言。

## 5. 工程与数据

**Q5.1 数仓为什么自己造？**
两个原因。一是岗位是数据平台方向，但没有真实数仓权限也能把链路跑通；
二是**可复现**——固定随机种子，任何人 clone 后跑出的数字和 README 一致。
208 天 × 8 个分区 × 4 个端，明细 6656 行 + 增长 832 行 + 创作 7896 行。
更重要的是我**故意注入并登记了两个异常**（游戏分区播放量 −45%、PC 端 DAU +38%），
这样「归因归对了没有」才有客观答案，不靠人看着像。

**Q5.2 「今天」为什么不取系统时间？**
因为取了系统时间，同一份代码在不同日期跑出的数字不一样，
README 上的每个数字都不可复现。所以「今天」取的是数仓里的最大日期，
显式可配、可测。这算是一个小决定，但它决定了这个项目能不能被验证。

**Q5.3 查询执行有哪些安全边界？**
只允许 SELECT；表名必须已注册在知识库；列名必须在表的字段清单里且匹配标识符正则；
所有筛选值走参数绑定、绝不拼字符串；查 DWD/DWS 明细层必须带日期区间
（这条同时也是治理规则 G01 的执行侧）。
另外「去重指标跨维度不可加」也在这里兜住了：`活跃UP主数` 按分区拆开后不能相加，
代码显式返回「不可加」，而不是硬算一个看起来正常的数。

**Q5.4 Agent 循环有什么约束？**
步数预算（问答 6 步、分析 8 步、治理 4 步），**跑满预算就停下来说明卡在哪，不无限重试**；
每一步（工具名 + 参数 + 观察结果 + 耗时）都留 trace，可被评测读取、可被复盘。
工具失败返回 `ok=False` 而不是空结果 —— 静默兜底是最贵的一类污染，
它会让「没查到」和「查到是 0」混在一起。

**Q5.5 这个项目跑得动吗？**
99 项测试约 58 秒；143 条评测用例全量跑一遍是秒级；整个项目只依赖 PyYAML。
网页自测台只用标准库，不引任何前端框架。

## 6. 已知弱点：怎么回答

**Q6.1 你这个是玩具数据吧？**
是模拟数据，我在 README 的「诚实的局限」里写明了。但我要强调：
**数据是模拟的，口径体系、消歧逻辑、评测方法是真实的。**
比如「完播率 vs 有效播放率」「人均播放时长 vs 人均使用时长」这些口径混淆，
是数据平台里真实存在的类问题。我造数仓的目的是让这条链路**可以被端到端验证**，
而不是展示我调过多少数据。

**Q6.2 没接大模型，算什么 Agent？**
我把 Agent 定义为「有目标、能规划、会调工具、有预算、留痕迹」的系统，
而不是「调用了 LLM」。这个项目里：规划器产出工具调用序列、循环执行并观察结果、
有步数预算、全程 trace、三个场景共用同一套循环。
**模型在这里是可替换的一层**，我把接口留出来了，但没做对照实验，所以不给数字。

**Q6.3 你这个产品上线后最大的风险是什么？**
我认为是**知识库口径与指标平台分叉** —— 回答「看起来很对但是错的」。
我的对策是把原始语料作为唯一真相源 + 产物新鲜度护栏，V1 起改为从指标平台同步、冲突以平台为准。
第二风险是**反问过多导致采纳率下降**，用户绕回原来的提需求路径，
对策是阈值可配 + 把高频歧义沉淀成推荐口径。
第三是治理误报导致开发把检查关掉，那比没有检查更糟，所以每条规则必须给证据、必须有反向用例。

## 7. 现场演示脚本（3 分钟）

```bash
# 1. 知识库：从非结构化语料拆出结构化条目
python scripts/build_kb.py                 # 32 指标 / 6 模型 / 10 规则 / 148 知识块
python -m dataagent.cli kb stats           # 看条目数与重复别名

# 2. 三个场景
python -m dataagent.cli ask "最近7天播放量是多少"      # 数 + 口径 + 证据
python -m dataagent.cli ask "留存率是多少"             # 反问：次日留存率 / 7日留存率
python -m dataagent.cli ask "帮我导出所有用户的手机号"  # 拒绝
python -m dataagent.cli analyze "2026-09-04 到 2026-09-10 播放量为什么降了"   # 主因=游戏分区
python -m dataagent.cli govern --sql "SELECT * FROM dws_video_daily"        # G01 + G02

# 3. 评测有牙齿
python -m dataagent.cli eval               # 143 条 · 五维
python -m dataagent.cli mutate             # 6 个变异体 6/6 被抓

# 4. 能点的自测台
python -m dataagent.cli studio             # 浏览器打开，四个 Tab
```

演示时优先点这三条，因为它们分别展示「口径管住了」「不编数字」「评测有牙齿」。

## 8. 可以反问面试官的问题

1. 数据平台现在的口径权威源是哪里？Agent 的回答如果和指标平台不一致，业务方会信谁？
2. 这个岗位前三个月最想验证的一个假设是什么？是「业务愿意用自然语言问数」，还是「Agent 能降低治理成本」？
3. 评测这块现在是怎么做的？有没有真实用户的提问日志可以拿到？
