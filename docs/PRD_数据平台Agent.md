## 1. 背景与要解决的问题

数据平台已经沉淀了大量指标、表和数据规范，但**「知识在那儿」和「人能顺畅用上」之间有一段很长的路**。这段路是三件事的成本：

| # | 问题 | 具体表现 | 当前成本 |
|---|---|---|---|
| P1 | **口径不一致** | 同一个「播放量」，指标平台、看板、分析师自己的 SQL 各有一份实现。同一天的数能差出两位数百分比，且**没有任何一方报错** | 每次对账平均要拉三方人；口径分叉后历史数据不可比 |
| P2 | **取数门槛高** | 业务方想问「上周游戏分区的完播率」，要先知道这个指标在指标平台叫什么、在哪个表、口径是什么，再写 SQL 或提需求排期 | 简单取数要走 1 次需求流转；复杂归因要走数天 |
| P3 | **治理靠人审** | 分区过滤缺失、`SELECT *`、敏感字段未脱敏、口径硬编码这类问题，主要靠上线评审时人肉看 SQL | 漏一个就是一次全表扫描或一次数据外泄风险 |

> **调研口径的诚实说明**：本 PRD 的问题定义来自公开的业务常识与数据平台通用实践，以及本项目在模拟数仓上的验证，**不是真实用户访谈**。原型阶段的目标是「把链路跑通、把口径管起来、把评测建起来」；真实访谈与样本量验证属于 V1 启动前的必做项（见 `docs/产品方案.md` §4）。

## 2. 目标与非目标

### 2.1 目标

1. 让业务方**用大白话问到数**，并且拿到的不只是数字，还有**口径和证据**。
2. 口径分不清时**先反问，不猜** —— 猜错的口径会一路污染到结论，而且没人会发现。
3. 让「为什么变了」这类归因从「提需求等排期」变成「问一句就有贡献度分解」。
4. 把数据规范变成**可执行的检查**，让治理从「人审」变成「工具先过一遍」。

### 2.2 非目标（本期明确不做）

- **不做**新的指标平台。指标口径的**权威源仍在指标平台**，本产品只做消费侧与治理侧。
- **不做**自助 BI 拖拽。不做看板、不做图表编辑器。
- **不做**个体明细查询。任何涉及用户/UP 主粒度明细的问法一律拦截，走数据权限流程。
- **不做**写操作。查询层只允许 `SELECT`。

## 3. 用户与场景

| 用户 | 核心 Job-to-be-done | 现在怎么做 | 用本产品之后 |
|---|---|---|---|
| 业务运营 | 「上周这个活动的效果怎么样」 | 找分析师提需求，等 1~3 天 | 直接问，拿到数 + 口径 + 维度拆分 |
| 数据分析师 | 「这个指标为什么掉了，是不是某个分区的问题」 | 自己写 SQL 逐维度下钻，重复劳动 | 让 Agent 先跑一遍贡献度归因，人只做复核 |
| 数据开发 | 「这段 SQL 能不能提交」 | 靠评审经验 + 治理同学人工看 | 提交前先过一遍规则检查，出问题清单 |

### 3.1 用户故事（含验收要点）

- **US-1**：作为运营，我想用日常说法问一个数，并且**看到这个数的口径**，这样我和别人对账时能说清用的是哪个口径。
- **US-2**：作为运营，当我的问法对应多个口径时，我希望**系统先问我一句**，而不是给我一个不知道对不对的数。
- **US-3**：作为分析师，我想问「为什么降了」，并拿到**按贡献度排序的维度拆解**，而不是一堆我自己还得再算的明细。
- **US-4**：作为数据开发，我想在提交前知道这段 SQL 触犯了哪些规范，以及**该怎么改**。
- **US-5**：作为数据安全同学，我要确保**个体明细和敏感字段不会被 Agent 吐出来**，无论用户怎么问。

## 4. 功能设计

### 4.1 模块一：数据智能问答

**一句话**：自然语言 → 指标口径 → 查询计划 → 执行 → 带口径与证据的回答。

| 编号 | 功能点 | 说明 |
|---|---|---|
| F1.1 | 指标检索与消歧 | 在 32 个已注册指标上做检索；命中多个且分不开时**反问**，不是取最高分 |
| F1.2 | 问法解析 | 时间（今天/昨天/最近N天/上周/上月/本月/今年以来/显式区间/某年某月）、维度（按分区/各端…）、筛选（游戏分区、iOS 端…） |
| F1.3 | 查询计划与执行 | 编译成受约束的 SQL：表必须已注册、列必须在字段清单里、筛选值参数绑定、明细层必须带日期区间 |
| F1.4 | 回答与证据 | 数字 + 口径定义 + 计算方式 + 来源表 + 口径负责人 + 引用的知识块 id |
| F1.5 | 越权与敏感拦截 | 手机号/身份证/设备号/用户明细/`up_id`/`user_id` 等问法直接拒绝并引导权限流程 |

**关键交互流程**

```
用户提问
  ├─ 命中越权/敏感问法 ──────────────────────→ 拒绝 + 引导权限流程
  └─ 指标检索
       ├─ 无候选 ────────────────────────────→ 说明「指标平台未注册」+ 建议补充关键词
       ├─ 多候选且分不开（top2 ≥ 0.8 × top1）→ 反问：列出可选口径，**不给数字**
       └─ 唯一候选 → 读口径 → 解析时间/维度/筛选 → 编译执行
                        ├─ 执行失败（如缺日期区间）→ 报错并回显查询计划
                        └─ 成功 → 回答（数 + 口径 + 证据块）
```

**边界与异常分支**

- **子串包含不算口径冲突**：「人均播放时长」里含「播放时长」，问得越具体不该越被反问。判定规则是**只有两个别名都出现在问题里**时才消解歧义；用户只打「播放」这种片段时两个口径是真分不开，必须反问。
- **去重指标跨维度不可加**：`活跃UP主数` 按分区拆开后不能相加，系统显式返回「不可加」而不是硬算一个数。
- **分母为 0** 的比率返回「不可计算」并说明原因，不返回 0。

### 4.2 模块二：自动化数据分析

**一句话**：问「为什么变了」，自动完成定基期 → 环比 → 异常检测 → 维度贡献度归因。

| 编号 | 功能点 | 说明 |
|---|---|---|
| F2.1 | 基期自动对齐 | 自动取**等长**的前一区间做对比（7 天对 7 天），避免工作日/周末构成不同造成的伪变化 |
| F2.2 | 异常检测 | 稳健 z-score（中位数 + MAD），不用均值/标准差 —— 均值会被异常本身拉走，导致大异常把自己藏起来 |
| F2.3 | 贡献度归因 | 把 `当前值 − 基期值` 拆到维度每个取值上，输出 delta 与贡献占比；**按 \|delta\| 排序**，不是按维度值大小 |
| F2.4 | 结论生成 | 主因 + 次因 + 口径说明；整体波动 <1% 时也提示「维度内部仍有分化」 |

**为什么不用「哪个维度值最大」当主因**：最大的维度值可能根本没变化。归因要看的是**变化量**。

### 4.3 模块三：数据治理助手

**一句话**：输入 SQL / 表名 / 待注册指标，输出问题清单。

| 编号 | 功能点 | 说明 |
|---|---|---|
| F3.1 | SQL 规则检查 | 10 条规则（G01~G10），输出 规则号 + P0/P1/P2 + 命中证据 + 修复建议 + 责任组 |
| F3.2 | 表命名体检 | 分层前缀（ods/dwd/dws/ads/dim）、小写下划线 |
| F3.3 | 表健康度画像 | 行数、NULL 计数、主键重复组数、数据区间 |
| F3.4 | 指标重复建设检测 | 新指标口径与已注册指标做相似度比对，超阈值提示复用或合并 |

**已实现的规则（节选）**

| 规则 | 级别 | 判什么 |
|---|---|---|
| G01 分区过滤缺失 | P0 | 查 dwd_/dws_ 表但 where 里没有 `date` |
| G02 禁止 SELECT * | P1 | select 列表出现 `*` |
| G03 敏感字段未脱敏 | P0 | `up_id`/`user_id`/`phone`/`device_id` 未包在 `mask_*()` 里 |
| G04 指标口径硬编码 | P1 | SQL 里直接写比率计算，未引用指标平台 |
| G08 JOIN 缺关联条件 | P0 | 有 `join` 但没有 `on` |

> 规则是**数据驱动**的：规则文本写在知识库语料里，代码只实现「怎么判」。加规则改 wiki，不改代码。

## 5. 流程梳理

### 5.1 Agent 主循环（三个模块共用）

```
规划器 → 工具调用 → 观察结果 → 再规划 → … → 最终答复
        ↑____________________________|
        步数预算（问答 6 步 / 分析 8 步 / 治理 4 步）
```

- **跑满预算就停下来说明卡在哪**，不无限重试。
- 每一步（工具名 + 参数 + 观察结果）都留 trace，可被评测读取、可被复盘。
- 规划器与循环解耦：换 LLM 规划器时，循环、预算、trace、评测都不用动。

### 5.2 端到端（以「上周游戏分区完播率为什么降了」为例）

```
① 检索指标 → 命中 完播率（唯一候选）
② 读口径   → 分子分母、来源表、口径负责人、易混指标（有效播放率）
③ 解析问法 → 时间=上周(2026-09-14~09-20)；筛选=category:游戏
④ 取当前值 → 汇总层查询
⑤ 取基期   → 自动前移 7 天
⑥ 逐维度归因 → category / platform
⑦ 输出结论 → 主因 + 贡献度 + 口径说明 + 证据块
```

## 6. 数据结构与接口（关键对象）

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `Metric` | id / name / domain / definition / formula / table / dimensions / unit / value_type / level / owner / aliases / confusable_with / caveats | 知识库里的指标条目 |
| `Chunk` | id / metric_id / kind / text | 知识拆解后的原子知识点，回答引用的是它 |
| `QueryPlan` | metric_id / table / dimensions / filters / start / end / limit | 自然语言到 SQL 的中间表示 |
| `ToolCall` / `Step` / `AgentTrace` | 工具名、参数、观察结果、耗时、步数 | 可复盘、可评测 |
| `Finding` | rule_id / severity / evidence / fix / owner | 治理问题清单条目 |
| `CaseScore` | accuracy / reasoning / adaptation / efficiency / experience | 五维评分 |

## 7. 验收标准

| 功能 | 验收条件（可执行） |
|---|---|
| F1.1 消歧 | 13 类歧义问法全部触发反问；具体问法（如「人均播放时长」）不被反问 |
| F1.4 回答完整性 | 每条回答必须含：数值 + 口径定义 + 计算方式 + 来源表 + 口径负责人 + 至少 1 个证据块 |
| F1.5 越权拦截 | 10 类越权/敏感问法全部拒绝，且不返回任何数值 |
| F2.3 归因 | 对两个登记在案的注入异常，主因维度与维度值必须命中（游戏分区 / PC 端） |
| F3.1 规则检查 | 21 条 SQL 用例的规则召回与精确率按 F1 计分 |
| 全局 | 143 条用例五维全量跑通；6 个变异体全部被抓；`pytest` 全绿 |

> 验收不是「人工看一眼觉得对」，而是**可执行、可复现的**：`python -m dataagent.cli eval` 与 `python -m dataagent.cli mutate` 的退出码就是验收结论。

## 8. 依赖、风险与本期不做

### 依赖

- **指标平台**：口径权威源。本产品的知识库需要与其对齐（当前用模拟语料替代）。
- **数仓权限**：查询层需要只读账号，且受治理规则约束。
- **数据安全**：敏感字段的脱敏函数由安全组提供。

### 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 知识库口径与指标平台分叉 | 回答「看起来很对但是错的」 | 原始语料作为唯一真相源 + 产物新鲜度护栏；上线后改为从指标平台同步 |
| 用户问法超出覆盖范围 | 答不上来或答错 | 宁可拒绝/反问，不给低置信度答案 |
| 反问太多导致体验差 | 采纳率下降 | 消歧阈值可配；把高频歧义问法沉淀成「推荐口径」 |
| 权限绕过 | 数据外泄 | 拦截在 Agent 层 + 查询层双重校验，明细层强制分区过滤 |
| 治理误报 | 开发关掉检查 | 规则命中必须给证据；规则只扫数据区不扫散文 |

### 本期不做

图表与看板、自助拖拽、多轮追问的记忆、跨库联邦查询、写操作、多维度交叉归因（辛普森悖论检查）。
