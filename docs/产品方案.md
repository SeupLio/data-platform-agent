# 数据平台 Agent · 产品方案

> PRD 回答「做成什么样」，这份回答「**为什么做、先做哪一块、怎么衡量做成了**」。
> 与 PRD 的分工：`docs/PRD_数据平台Agent.md` 定义功能与验收，本文定义策略与节奏。

---

## 1. 为什么现在做

数据平台的能力建设已经过了「有没有数据」的阶段，卡点在**「知识有，但用不上」**：

| 现状 | 成本形态 | 谁在付 |
|---|---|---|
| 口径散落在 wiki、指标平台、分析师 SQL 三处 | 每次对账拉三方人；口径分叉后历史不可比 | 业务 + 分析师 |
| 取数要跨「知道叫什么 → 知道在哪张表 → 会写 SQL」三道门槛 | 简单取数走需求流转；复杂归因走数天 | 业务运营 |
| 治理规则靠上线评审人肉看 | 漏一条 = 一次全表扫描或一次外泄风险 | 数据开发 + 安全 |

**为什么现在**：Agent 这条技术路线第一次让「自然语言 → 受约束的结构化查询」变得可控 ——
只要**口径是结构化的**、**执行是受约束的**、**结果是被评测的**，就能把上面三件事同时往前推一步。
反过来说，这三件事缺任何一件，做出来的就是个会编数字的聊天框。

## 2. 目标用户与他们的 Job

| 用户 | Job-to-be-done | 成功的样子 |
|---|---|---|
| 业务运营 | 「我不想学 SQL，也不想等排期，我想知道这个数是多少、它是什么意思」 | 问一句就得到数 + 口径，敢拿去开会 |
| 数据分析师 | 「我不想把时间花在重复的逐维度下钻上」 | Agent 先出归因初稿，人只做复核与深挖 |
| 数据开发 | 「我提交前想知道这段 SQL 会不会被治理打回」 | 提交前先过一遍，问题清单直接告诉怎么改 |
| 数据安全 / 治理 | 「我不想靠人肉审计发现口径分叉和敏感字段外泄」 | 规则自动跑，误报低到不用关掉 |

## 3. 产品定位与边界

**定位**：数据平台的**消费侧入口**与**治理侧前置闸门**。

```
        指标平台（口径权威源）
              │  同步口径
              ▼
   ┌──────────────────────────────┐
   │      数据平台 Agent           │
   │  ① 智能问答  ② 自动分析        │  ← 消费侧入口
   │  ③ 治理助手                    │  ← 治理侧前置闸门
   └──────────────────────────────┘
              │  只读、受约束
              ▼
            数仓 / 湖仓
```

**明确不做**（边界写清楚，比写清楚做什么更重要）：

| 不做 | 理由 |
|---|---|
| 新建指标平台 | 会制造第二份口径真相源，正好是我们要解决的问题 |
| 自助 BI / 看板 / 图表 | 已有工具链，重做没有增量 |
| 个体明细查询 | 合规风险远大于产品收益；一律走权限流程 |
| 写操作 / 数据回填 | 只读是最小攻击面 |
| 用大模型直接生成并执行 SQL | 时间区间和口径这类东西错了没有痕迹；本期用确定性规则，模型只做「把用户的话改写成规则能认的形式」 |

## 4. 落地路径

### MVP（本仓库已完成的部分）

**范围**：三个场景的确定性链路 + 知识库拆解 + 五维评测与变异测试。

| 交付 | 验收 |
|---|---|
| 知识库：32 指标 / 6 数据模型 / 10 治理规则 / 148 知识块 | 产物可从原始语料逐字节重建；指标引用的字段必须在来源表字段清单里 |
| 智能问答 | 13 类歧义问法全部反问；10 类越权问法全部拒绝；回答必带口径与证据 |
| 自动分析 | 对 2 个登记在案的注入异常，主因维度与维度值必须命中 |
| 治理助手 | 21 条 SQL 用例 + 7 条表名用例按 F1 计分 |
| 评测 | 143 条用例五维跑通；6 个变异体全部被抓；`pytest` 99 项全绿 |

**MVP 阶段刻意不做的事**：接真实模型、接真实数仓、多轮对话、图表。

### V1（需要外部依赖）

| 事项 | 依赖 | 验收 |
|---|---|---|
| 知识库与指标平台对齐 | 指标平台开放口径接口 | 知识库条目与指标平台逐条可对账；不一致时以平台为准 |
| 接真实数仓只读账号 | 数仓权限 | 同一问题在真实数仓上的答案与本仓原型一致（口径一致前提下） |
| 真实用户访谈与样本量 | 业务方配合 | 高频问法 Top 50 覆盖率 ≥ 80% |
| LLM 规划器对照实验 | 模型额度 | 规则规划 vs 模型规划在同一套用例上跑对照；**只有真的跑过才给数字** |

### V2（探索）

多轮追问与上下文继承、多维度交叉归因（含辛普森悖论检查）、治理规则从「SQL 文本特征」升级为「真正的 SQL 解析」、口径变更影响面分析。

## 5. 成功指标

分四层。**原型上能量到的写基线，量不到的明确写「原型上量不到」** —— 不编数字。

| 层 | 指标 | 定义 | 原型上的基线 |
|---|---|---|---|
| 使用量 | 周活提问用户数 | 一周内至少提问 1 次的用户数 | 原型上量不到（无真实用户） |
| 使用量 | 提问到有效回答的转化率 | `kind=answer` 的提问 / 总提问 | 可测：143 条用例中 answer 类 120 条，占 83.9% |
| 质量 | 口径错误率 | 回答给出的指标口径与指标平台不一致的比例 | 原型上量不到（无平台对账）；可替代指标：歧义问法反问率 100%（13/13） |
| 质量 | 归因命中率 | 主因维度与维度值命中已知异常的比例 | 4/4（两个注入异常各覆盖 2 条用例） |
| 效率 | 首次有效回答延迟 | 从提问到返回回答的耗时 | ≤ 2000 ms（评测效率维预算，实测全部通过） |
| 效率 | 取数链路时长 | 从提问到拿到可用结论的端到端时长 | 原型上量不到（需真实业务链路对比） |
| 治理 | 规则召回率 | 已知问题被检出的比例 | 21 条 SQL 用例 + 7 条表名用例全量命中（F1 = 1.0） |
| 治理 | 规则误报率 | 合规 SQL 被误判的比例 | 8 条合规用例 0 误报 |
| 采纳 | 回答被采纳率 | 用户直接使用/转发回答的比例 | 原型上量不到 |

> ⚠️ **不要拿 MVP 的 1.0000 当产品指标**。那是在自己造的用例上跑出来的回归基线，
> 说明的是「实现没退化」，不是「用户满意」。真正说明评测有效的是变异测试 6/6 被抓。

## 6. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | 知识库口径与指标平台分叉 | 回答「看起来很对但是错的」，比答不上来更危险 | 原始语料唯一真相源 + 产物新鲜度护栏；V1 起改为从指标平台同步，冲突以平台为准 |
| R2 | 用户问法超出覆盖范围 | 答不上来或答错 | 宁可拒绝/反问，不给低置信度答案；无候选时明确说「指标平台未注册」 |
| R3 | 反问过多导致体验下降 | 采纳率下降，用户绕回原来的提需求路径 | 消歧阈值可配（当前 0.80）；把高频歧义问法沉淀为「推荐口径」；同一用户重复问同一口径时记住选择 |
| R4 | 权限绕过 / 敏感信息外泄 | 合规事故 | Agent 层拦截 + 查询层双重校验（只 SELECT、列白名单、明细层强制分区过滤、筛选值参数绑定） |
| R5 | 治理误报太多 | 开发直接把检查关掉，比没有更糟 | 每条命中必须带证据；规则只扫数据区不扫散文；每条规则配反向用例（合规 SQL 必须 0 误报） |
| R6 | 归因结论被过度解读 | 用户把「贡献度」当成「因果关系」 | 结论里固定带口径说明；贡献度是分解不是因果，V2 才考虑引入对照与显著性 |
| R7 | 与现有指标平台职责重叠 | 组织内推不动 | 定位为消费侧 + 治理侧，不碰口径定义；口径变更流程仍走平台 |
