# 数据平台 Agent · 知识库构建说明

> 这份文档对应岗位 JD 的「知识库构建」：**知识体系搭建 → 内容录入 → 知识拆解 → 结构化整理 → 迭代优化**。
> 关键立场：**知识库不是一份文档，是一份可以被程序校验、被检索、被引用的结构化数据。**

---

## 1. 知识体系的三层结构

| 层 | 回答什么问题 | 条目数 | 真实字段 |
|---|---|---|---|
| **指标（Metric）** | 「这个数是什么、怎么算、谁负责」 | 32 | `id` `name` `domain` `definition` `formula` `table` `dimensions` `unit` `value_type` `level` `owner` `aliases` `confusable_with` `caveats` |
| **数据模型（DataModel）** | 「这个数从哪张表来、能按什么拆、上下游是谁」 | 6 | `id`（表名） `layer` `domain` `grain` `partition_key` `columns` `upstream` `downstream` `owner` `notes` |
| **数据规范（PolicyRule）** | 「什么样的做法是不合规的、怎么改、谁负责」 | 10 | `id` `name` `severity` `target` `logic` `fix` `owner` |

**指标按业务域分五类**：消费（播放/时长/完播）、社区互动（点赞/投币/收藏/分享/评论/弹幕/互动率）、用户增长（DAU/新增/留存/时长）、商业化（付费转化/ARPU/大会员/广告收入）、创作（投稿/过审/活跃UP主/涨粉）。

**指标分两层**：原子指标（可加，如 `播放量`）与派生指标（比率，如 `完播率`）。
这个区分不是分类癖 —— 它决定了查询层能不能跨维度相加（见 §6.3）。

**数据模型分四层**：DWD（明细）→ DWS（汇总）→ ADS（应用），加 DIM（维表）。
每张表登记了字段清单与上下游血缘，指标引用的字段必须在这张表的字段清单里（有硬校验）。

## 2. 拆解流水线

```
data/raw/*.md（非结构化 wiki 语料）
      │  ① 分块      split_blocks()      按 `## ` 标题切块
      │  ② 字段抽取  parse_fields()      按 `- 键：值` 抽取
      │  ③ 归一      build_metrics()     别名/维度/易混 拆成列表；指标编码归一
      │  ④ 一致性校验 build_all()        指标 ↔ 表 ↔ 字段 三方对齐
      │  ⑤ 易混识别  build_confusable_pairs()  单向 → 无向
      │  ⑥ 知识拆解  build_chunks()      一个指标 → 若干原子知识点
      ▼
data/built/*.yaml（metrics / models / policies / chunks / confusable_pairs / meta）
```

### 2.1 输入长什么样

原始语料刻意做成**真实 wiki 的样子**（段落 + 字段行），不是已经结构化的数据：

```markdown
## 完播率

- 指标编码：finish_rate
- 业务域：消费
- 口径定义：完播次数占播放次数的比例，衡量内容吸引力
- 计算方式：sum(finish_cnt) / sum(play_cnt)
- 来源表：dws_video_daily
- 支持维度：date, category, platform
- 单位：百分比
- 数值类型：ratio
- 指标层级：派生指标
- 口径负责人：数据平台-消费数据组
- 别名：完播率 | 完整播放率
- 易混指标：有效播放率
- 注意事项：分子分母必须同维度同口径，禁止跨表拼接
```

三个原始文件：`metric_glossary.md`（32 指标）、`model_spec.md`（6 模型）、`governance_rules.md`（10 规则）。

### 2.2 产物长什么样

`data/built/metrics.yaml` 是**排序 + 固定序列化**的 YAML（`sort_keys=True`、`allow_unicode=True`），
所以「同样输入 → 同样字节」。`meta.yaml` 记录三份语料的 sha256 前 16 位与各层条目数，
用来判断产物是不是最新的。

## 3. 拆解时的硬校验（每条都由一次真实事故换来）

全部在 `src/dataagent/knowledge/build.py`，失败一律抛异常，**不做兜底**：

| 校验 | 防的是什么事故 |
|---|---|
| 原始语料文件缺失 | 静默生成一份空知识库，Agent 从此答不出任何东西却「不报错」 |
| 语料里没有任何 `## ` 分块 | 格式变了导致解析出 0 条，比解析错更隐蔽 |
| 指标缺少必填字段 | 半条知识入库，检索命中它但拿不到口径 |
| **计算式解析不出来** | 口径不可计算 → 错误口径会一路污染到 SQL 和数字，而且没人发现 |
| 指标编码重复 | 两条知识抢同一个 id，检索取哪条不确定 |
| 数据模型缺字段清单 | 后续「字段是否存在于表中」的校验失去依据 |
| 治理规则标题不规范 / 缺字段 | 规则跑不起来，但看起来「有 10 条规则」 |
| 易混指标在词典里找不到 | 消歧指向一个不存在的口径 |
| **指标引用了未注册的表** | 查询编译时才炸，且错误信息不指向知识库 |
| **指标依赖的字段不在表的字段清单里** | 最容易悄悄坏掉的一致性：表和指标各自改，谁都不报错 |

最后两条是最有价值的两条 —— 它们把「知识库自相矛盾」从**运行期偶发错误**变成**构建期必然失败**。

## 4. 知识拆解：一个指标 → 若干原子知识点

`build_chunks()` 把一个指标拆成 5 类 chunk：

| kind | 内容 | 例（`play_cnt`） |
|---|---|---|
| `definition` | 口径定义 | `播放量（次）：统计周期内视频被播放的次数，每一次起播计 1 次，同一用户重复播放重复计数` |
| `formula` | 计算方式 + 来源表 | `播放量 的计算方式：sum(play_cnt)，来源表 dws_video_daily` |
| `dimension` | 支持维度 | `播放量 支持维度：date、category、platform` |
| `caveat` | 口径注意事项 | `播放量 口径注意：与「播放人数」是一对高频混淆口径…` |
| `confusable` | 易混指标 | `播放量 易混指标：播放人数` |

chunk id 形如 `play_cnt::definition`。当前共 **148 个 chunk**。

**为什么回答要引用 chunk 而不是整篇文档**：
「证据」必须能指到具体一句。如果回答里写「依据：播放量口径」，
用户没法验证你读的是定义还是注意事项；写「依据：`play_cnt::formula`」才能对得上。

## 5. 易混指标：wiki 单向写，检索双向用

原始语料里易混关系是**单向**写的（只在其中一个指标上写「易混指标：播放人数」），
因为 wiki 页面天然是各写各的。但检索时必须当**无向**用，否则「从 B 查 A」会漏掉消歧。

`build_confusable_pairs()` 把它归一化成无向对（排序后去重）。当前 **12 对**：

| # | 易混对 | 混淆点 |
|---|---|---|
| 1 | `play_cnt` 播放量 ↔ `watch_uv` 播放人数 | 计次 vs 去重计人 |
| 2 | `finish_rate` 完播率 ↔ `valid_play_rate` 有效播放率 | 走到结尾 vs 播放≥30 秒 |
| 3 | `finish_cnt` 完播次数 ↔ `valid_play_cnt` 有效播放次数 | 同上，计次版 |
| 4 | `interaction_rate` 互动率 ↔ `like_rate` 点赞率 | 全量互动 vs 只算点赞 |
| 5 | `interaction_rate` 互动率 ↔ `triple_rate` 三连率 | 行为次数之和 vs 用户×稿件去重 |
| 6 | `like_rate` 点赞率 ↔ `triple_rate` 三连率 | 单行为 vs 复合行为 |
| 7 | `retain_1d_rate` 次日留存率 ↔ `retain_7d_rate` 7日留存率 | 窗口不同，共用分母 |
| 8 | `avg_play_duration` 人均播放时长 ↔ `avg_usage_duration` 人均使用时长 | 分母不同（播放人数 vs DAU） |
| 9 | `duration_sec` 播放时长 ↔ `usage_sec` 使用时长 | 只算视频 vs 全站 |
| 10 | `dau` DAU ↔ `watch_uv` 播放人数 | 全站访问 vs 视频消费 |
| 11 | `comment_cnt` 评论数 ↔ `danmu_cnt` 弹幕数 | 独立实体 vs 时间轴 |
| 12 | `audit_pass_cnt` 过审数 ↔ `upload_cnt` 投稿数 | 提交 vs 通过 |

## 6. 检索与消歧

实现在 `src/dataagent/knowledge/index.py`。检索的产出不是「最像的那个」，而是
`Resolution`（是否要反问、候选是谁、为什么）。

### 6.1 四种匹配形态与打分

| 形态 `match_kind` | 条件 | 分数 |
|---|---|---|
| `exact` | 问题归一化后与别名完全相同 | 100 |
| `in_query` | **别名出现在问题里** | `60 + min(len(alias), 10)` |
| `query_in` | **问题出现在别名里**（用户只打了片段） | 50 |
| `ngram` | 字符 bigram 的 Jaccard 重合度 | `60 × 重合度` |

补充信号（仅在最高分 < 60 时生效，避免业务域词把一堆指标拉平）：命中业务域 +6；
与口径定义的 bigram 重合度 ×20。

### 6.2 澄清阈值

```python
CLARIFY_RATIO = 0.80   # 第二名 ≥ 0.8 × 第一名 → 视为分不开
MIN_SCORE = 12.0       # 最高分低于它 → 视为「知识库没覆盖」
```

- 分不开 → `need_clarification=True`，**不给数字**，列出可选口径；
- 没覆盖 → 明确告知「指标平台未注册」，建议补充关键词。

### 6.3 ⭐ 子串包含 ≠ 口径冲突

这是消歧里最反直觉、也最影响体验的一条规则。

**反例（该消解，不该反问）**：

```
问：「最近7天人均播放时长是多少」
命中：人均播放时长 66.0（别名出现在问题里）
      播放时长     64.0（「播放时长」也出现在问题里）
```

如果把它当歧义，就会出现「**问得越具体越被反问**」——产品上不可用。

**正例（必须反问）**：

```
问：「播放」
命中：人均播放时长 51.25 / 播放时长 51.25 / 完播次数 51.18
```

用户只打了一个片段，几个口径是真分不开，必须反问。

**判定规则**：只有当两个候选的命中形态**都是 `in_query`（别名确实出现在问题里）**，
且更长的别名把更短的整个包含进去时，才消解歧义（取更精确的那个）。
`query_in`（问题只是别名的一个片段）**不参与消解**。

同一条规则也解决了这类问题：

| 问法 | 不消解会怎样 | 消解后 |
|---|---|---|
| 上月有效播放次数是多少 | 被「播放次数」拖进反问 | 正确选中 `valid_play_cnt` |
| 本月人均使用时长为什么降了 | 被「使用时长」拖进反问 | 正确选中 `avg_usage_duration` |

### 6.4 别名唯一性

同一个别名指向两个指标 = 检索必然挑一个，而挑哪个没人说得清。
`KnowledgeIndex.duplicated_aliases()` 专门暴露这个问题，并有护栏测试
`test_no_duplicate_alias_across_metrics` 断言它为空。

（建设过程中真的踩到过：`人均消费时长` 同时被挂在 `人均播放时长` 和 `人均使用时长` 上，
已删除其中一个，改为 `人均视频时长`。）

## 7. 迭代机制：加一个指标要动什么

1. 在 `data/raw/metric_glossary.md` 追加一个 `## 指标名` 块，填齐 13 个字段
   （`指标编码` 必填且唯一）；
2. 如果来源表或字段是新的 → 先在 `data/raw/model_spec.md` 里补上字段清单；
3. 跑 `python scripts/build_kb.py`；
4. 跑 `python -m dataagent.cli kb stats` 看条目数、易混对、重复别名；
5. 跑 `python -m pytest tests -q`。

**会先红的护栏**：

| 你漏了什么 | 哪条护栏先红 |
|---|---|
| 忘了重跑构建 | `test_build_is_deterministic_and_fresh` |
| 编码重复 / 别名撞车 | `test_no_duplicate_alias_across_metrics` |
| 引用了不存在的表或字段 | 构建期直接抛 `KnowledgeBuildError`（跑不到测试就炸了） |
| 易混指标写了个不存在的名字 | 同上 |
| 计算式写错（如 `avg(...)`） | `test_every_metric_formula_is_computable` |

**新增治理规则**还要多做一件事：补用例 + 补一条**反向用例**（合规 SQL 必须 0 误报）。
只加「会红」的用例、不加「不该红」的用例，是治理类规则最常见的翻车方式 ——
误报多到开发直接把检查关掉，比没有检查更糟。
