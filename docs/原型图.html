产品说明

需求业务同学用大白话问数。口径选错比答不上来更危险——数字会错得毫无痕迹，所以回答必须「数 + 口径定义 + 证据」三件套齐出，分不清时先反问一句。
验收标准① 歧义问法 100% 反问、不猜（留存率）；② 越权/敏感问法 100% 拒绝并给出权限路径；③ 精确别名不误反问（人均播放时长 66.0 吞掉播放时长 64.0）；④ 每个回答可回溯到知识块 id；⑤ 置信度不足（< 12.0）不猜口径。

链路：定指标 → 取当前区间 → 取等长基线段 → 逐维度贡献度归因 → 输出结论

日粒度趋势

产品说明

需求用户不再问「是多少」，而是问「为什么变了」。Agent 要自动完成定指标、取数、取基线、归因，并把 delta 拆到每个维度值上说人话。
验收标准① 基线段与当前段等长、可复现；② 用贡献度分解而非「哪个维度值最大」——各维度值贡献之和还原整体 delta；③ 主因结论与登记异常对齐（2026-09-10 游戏分区 play_cnt factor 0.55、2026-09-16 pc 端 dau factor 1.38）；④ 任意维度值可下钻到日粒度明细。

产品说明

需求治理规范写在 wiki 上没人看。把它变成可执行的检查：贴一段 SQL、一张表名、一个待注册指标，立刻给出可派单的问题清单。
验收标准① 每条命中必须同时给出规则号、P0/P1/P2、命中证据、修复建议、责任组；② 级别可驱动拦截策略（P0 阻断提交）；③ 规则数据驱动，全库 10 条（8 条判 SQL / 1 条判表名 / 1 条判指标）；④ 判不出时不硬报——未命中即「可提交」。

产品说明

需求知识库不是一次性字典。它要能被业务组持续维护：一条指标改口径，问答、分析、治理三条链路同时生效。
验收标准① 一条指标的结构化字段完整（定义 / 公式 / 来源表 / 支持维度 / 单位 / 口径负责人 / 别名 / 易混 / 注意事项）；② 一条指标拆成可独立引用的知识块，全库 32 → 148；③ 易混关系双向可维护（12 对），消歧时直接可用；④ 从 wiki 到结构化产物有可重跑流水线与新鲜度护栏。
