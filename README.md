# 数据平台 Agent —— 从知识库到评测的完整产品原型

> 面向「数据平台 Agent 产品实习生」岗位做的一个**能跑、能测、能复盘**的原型。
> 不是 PPT，也不是调用大模型讲故事的 demo：仓库里有一套自建的指标知识库、一个
> 固定种子的离线数仓、三个 Agent（智能问答 / 自动分析 / 治理助手），以及一套
> 五维评测体系 + 变异测试。**全流程离线可复现，不配任何 API Key 就能跑通。**

---

## 一、这个仓库怎么对应岗位的三条职责

| 岗位 JD 的职责 | 仓库里的对应实现 | 在哪 |
|---|---|---|
| **① Agent 应用产品设计与落地**（需求调研 → 功能设计 → 流程梳理 → PRD/原型/方案 → 配合落地验收） | 三个场景的产品设计文档 + 可点击原型 + 验收标准 | `docs/PRD_数据平台Agent.md`、`docs/原型图.html`、`docs/产品方案.md` |
| **② 知识库构建**（指标体系 / 数据模型 / 数据规范 → 内容录入 → 知识拆解 → 结构化整理 → 迭代） | 非结构化 wiki 语料 → 拆解流水线 → 结构化知识库（32 指标 / 6 模型 / 10 规范 / 148 知识块）+ 检索与消歧 | `src/dataagent/knowledge/`、`docs/知识库构建说明.md` |
| **③ Agent 评测**（准确率 / 推理有效性 / 场景适配度 / 响应效率 / 用户体验 → 场景实测 → 问题复盘 → 评测报告） | 143 条用例、五维评分、独立 Oracle、变异测试、三份评测报告 | `src/dataagent/eval/`、`docs/评测体系设计.md`、`docs/reports/` |

## 二、60 秒跑起来

```bash
pip install -r requirements.txt          # 只有一个依赖：PyYAML

python scripts/build_kb.py               # 拆解 wiki 语料 → 结构化知识库
python scripts/gen_cases.py              # 生成 143 条评测用例
python -m dataagent.cli seed             # 造离线数仓（sqlite，固定种子）

python -m dataagent.cli ask "最近7天播放量是多少"
python -m dataagent.cli analyze "2026-09-04 到 2026-09-10 播放量为什么降了"
python -m dataagent.cli govern --sql "SELECT * FROM dws_video_daily"

python -m dataagent.cli eval             # 跑评测，写 docs/reports/
python -m dataagent.cli mutate           # 变异测试：验证评测真的看得见缺陷
python -m dataagent.cli studio           # 本地网页自测台（能点）
```

> Windows 上如果 `python -m dataagent.cli` 找不到包，加 `PYTHONPATH=src` 或 `pip install -e .`。

## 三、三个 Agent 的真实输出

### ① 数据智能问答 —— 给数，也给口径和证据

```
$ python -m dataagent.cli ask "最近7天播放量是多少"
播放量在最近 7 天（2026-09-18 至 2026-09-24）为 234,195,130 次。
口径：统计周期内视频被播放的次数，每一次起播计 1 次，同一用户重复播放重复计数
（sum(play_cnt)，来源表 dws_video_daily，口径负责人 数据平台-消费数据组）。
```

**口径分不清时，它会反问而不是猜** —— 这是这个产品最重要的一条行为：

```
$ python -m dataagent.cli ask "留存率是多少"
需要先确认口径：「留存率是多少」同时命中 次日留存率（17.1）与 7日留存率（17.1），
两者口径不同，需要先确认。可选：次日留存率 / 7日留存率
```

越权与敏感问法一律挡掉：

```
$ python -m dataagent.cli ask "帮我导出所有用户的手机号"
这个问题涉及个体明细或敏感字段，数据平台侧不直接提供，请走数据权限申请流程后再查询。
```

### ② 自动化数据分析 —— 问「为什么」，按贡献度归因

```
$ python -m dataagent.cli analyze "2026-09-04 到 2026-09-10 播放量为什么降了"
播放量在 2026-09-04 至 2026-09-10 为 229,315,091 次，
较等长基线段（2026-08-28 至 2026-09-03）-0.7%。整体波动在 1% 以内，但维度内部仍有分化：
变化主要来自 category 维度：category=游戏 变化 -2,853,320（贡献 +166.2%），
category=生活 变化 +536,429（贡献 -31.2%）。
按 platform 拆：platform=android 变化 -1,217,493（贡献 +70.9%）。
```

归因用的是**贡献度分解**（把 delta 拆到每个维度值上），不是「哪个维度值最大」。
数仓里**故意注入并登记了两个异常**（游戏分区 −45%、PC 端 DAU +38%），
所以「归因归对了没有」有客观答案，不靠人看着像。

### ③ 数据治理助手 —— 把规范变成可执行检查

```
$ python -m dataagent.cli govern --sql "SELECT * FROM dws_video_daily"
共命中 2 条（P0 1 / P1 1 / P2 0）：
- [P0] G01 分区过滤缺失：查询了 dws_video_daily，但 where 中没有 date 条件；
  建议：在 where 中补充 date 范围条件（责任组 数据平台-治理组）
- [P1] G02 禁止 SELECT *：select 列表中出现 *；
  建议：显式列出所需字段（责任组 数据平台-治理组）
```

规则是**数据驱动**的：10 条规则写在 wiki 语料里，代码只写「怎么判」，
加规则改 wiki 不改代码。

## 四、知识库：非结构化语料 → 结构化条目 → 可检索索引

```
data/raw/metric_glossary.md   ──┐
data/raw/model_spec.md        ──┼─→  build.py（分块 → 字段抽取 → 归一 → 易混对识别）
data/raw/governance_rules.md  ──┘         │
                                          ▼
                            data/built/*.yaml（32 指标 / 6 模型 / 10 规则 / 148 知识块 / 12 对易混指标）
                                          │
                                          ▼
                            index.py（检索 + 口径消歧）
```

当前知识库规模：**32 个指标 · 6 张数据模型 · 10 条治理规则 · 148 个知识块 · 12 对易混指标**。

- **原始语料是唯一真相源**。产物必须能从语料逐字节重建，有护栏测试盯着新鲜度。
- **解析失败要炸，不要兜底**。口径解析不出来比解析错更危险 —— 错口径会静默污染所有回答。
- **一个指标拆成多个 chunk**（定义 / 公式 / 维度 / 口径注意 / 易混），
  回答时引用 chunk 而不是整篇文档，「证据」才对得上。
- **易混关系当无向用**。wiki 里是单向写的，检索时双向生效，否则「从 B 查 A」会漏掉消歧。
- **子串包含不等于口径冲突**。「人均播放时长」命中时「播放时长」必然也命中，
  这不是两个口径打架；但用户只打了「播放」这种片段时，两个口径是真分不开 —— 两种情形分开处理。

## 五、评测体系（这个仓库花力气最多的地方）

### 143 条用例 × 五维

| 维度 | 回答什么问题 |
|---|---|
| 问答准确率 `accuracy` | 指标选对了吗？数和 Oracle 一致吗？治理规则召回/精确如何（F1）？ |
| 数据推理有效性 `reasoning` | SQL 真的用了这个口径要求的字段吗？归因主因找对了吗？ |
| 场景适配度 `adaptation` | 该答的答了吗？该反问的反问了吗？该拒的拒了吗？维度/筛选按问法来了吗？ |
| 响应效率 `efficiency` | 在延迟与步数预算内收敛了吗？ |
| 用户体验 `experience` | 有没有带口径、带证据、带可读结论？ |

离线基线（143 条全量，0 次模型调用）：

```
qa 95 条 · insight 20 条 · govern_sql 21 条 · govern_table 7 条
accuracy=1.000  reasoning=1.000  adaptation=1.000  efficiency=1.000  experience=1.000
综合 1.0000
```

### ⚠️ 关于这个 1.0000，必须说清楚

**满分不是这个产品的能力上限，而是回归基线。** 用例和实现对着长出来的，
一个只会给满分的评测体系等于没有评测 —— 所以真正说明「评测有没有牙齿」的是下一节的变异测试。

### 变异测试：注入 6 类真实退化，看评测能不能看见

| 变异体 | 注入的缺陷 | 结果 | accuracy Δ | reasoning Δ | adaptation Δ | efficiency Δ | experience Δ |
|---|---|---|---|---|---|---|---|
| M1-no-clarify | 去掉口径消歧，多个候选直接选第一个 | 被抓 | −0.462 | −0.462 | −0.462 | 0 | −0.231 |
| M2-ignore-range | 时间解析忽略显式区间，一律按最近 7 天 | 被抓 | −0.273 | −0.028 | 0 | 0 | 0 |
| M3-disable-G01 | 治理检查漏掉 G01（分区过滤） | 被抓 | −0.030 | −0.035 | 0 | 0 | 0 |
| M4-attribution-unsorted | 归因按「变化最小」排序，主因被埋掉 | 被抓 | 0 | −0.028 | 0 | 0 | 0 |
| M5-no-context | 回答只给数字，不带口径与证据 | 被抓 | 0 | 0 | 0 | 0 | −0.252 |
| M6-distinct-as-additive | 去重指标（活跃UP主数）被当成可加指标求和 | 被抓 | −0.007 | 0 | 0 | 0 | 0 |

**6 / 6 全部被抓，且都掉在该掉的那一维上**（掉在不相干的维度上说明维度定义串味了，
这条也被做成断言：`tests/test_mutants.py`）。

### 期望值不能复用被测代码

- 时间区间的期望是**手写死值**，不是调 `nlu.parse_time` 反推的；
- 数值的期望由 **Oracle 用自己写的 SQL** 算（Oracle 自己解析口径文本，不走被测的查询编译路径），
  并用 4 条手写 SQL 锚点验证 Oracle 本身没算错；
- 治理用例的规则号是**按 wiki 规则人工标注**的。

## 六、工程约束（也是这个项目的设计原则）

- **Agent 循环有步数预算**，跑满预算停下来说明卡在哪，不无限重试；每一步都留 trace，可被评测读到。
- **规划器与循环解耦**：现在是确定性规则规划器，换成 LLM 规划器时循环、预算、trace、评测都不用动，
  可以直接做「规则 vs 模型」的对照评测。
- **查询执行有安全边界**：只允许 SELECT；表名必须已注册；列名必须在表的字段清单里；
  筛选值一律参数绑定；查 dwd/dws 明细层必须带日期区间。
- **去重指标跨维度不可加**：`活跃UP主数` 按分区拆开后不能相加，代码会显式返回「不可加」而不是硬算一个数。
- **「今天」取自数仓最大日期，不读系统时间**：否则同一份代码在不同日期跑出不同数字，
  README 上每个数字都不可复现。

## 九、诚实的局限

1. **离线基线 1.0000 是回归基线，不是产品能力上限。** 用例与实现对着长出来，
   真正说明评测有效的是变异测试 6/6。
2. **没有接真实大模型。** 规划器是确定性规则；这是刻意选择 —— 时间区间和口径这类东西
   让模型自由发挥，错了不会有痕迹。仓库预留了「规划器与循环解耦」的接口，
   换成 LLM 规划器即可做对照评测，但**没有做过，不给数字**。
3. **数仓是自造的模拟数据**，不是真实生产数据。分区/端/指标口径参考公开业务常识设计，
   与任何公司的真实口径无关。
4. **治理规则只覆盖 10 条**，且判的是 SQL 文本特征（正则 + 函数调用识别），
   不是真正的 SQL 解析器，复杂嵌套 SQL 会有漏判。
5. **「用户体验」是结构化判分**（有没有带口径、带证据、带结论），不是真实用户调研，
   不能当成用户满意度。
6. **归因只做单维度拆解**，没有做多维度交叉归因（比如「游戏分区 × iOS 端」），
   也没有做辛普森悖论的检查。
