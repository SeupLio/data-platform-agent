# 数据平台 Agent（Data Platform Agent）

> 一个**离线可复现**的数据平台 Agent 产品原型：自建指标知识库 + 三个 Agent（智能问答 / 自动分析 / 治理助手）+ 五维评测体系与变异测试。
>
> 它回答的核心问题是：**当用户用自然语言向数据平台要一个数时，怎么保证拿到的不是「一个看起来很对的错数」？**
> 本项目的答案是三件事：口径是结构化的、执行是受约束的、结果是被评测的。

全流程不需要任何 API Key、不联网、不调用大模型 —— `pip install pyyaml` 之后即可完整跑通问答、分析、治理、评测与变异测试。

---

## 特性一览

| | |
|---|---|
| **三个 Agent** | 数据智能问答（给数 + 给口径 + 给证据）、自动化分析（贡献度归因）、治理助手（SQL/表规范检查） |
| **结构化知识库** | 32 指标 · 6 数据模型 · 10 治理规则 · 148 原子知识块 · 12 对易混指标，从非结构化 wiki 语料一键重建 |
| **离线数仓** | SQLite 模拟数仓（固定种子），内置 2 个登记在案的注入异常，让「归因对不对」有客观答案 |
| **五维评测** | 143 条用例 × 准确率/推理有效性/场景适配度/响应效率/用户体验，期望值由独立 Oracle 计算 |
| **变异测试** | 运行期注入 6 类真实退化，验证评测「有牙齿」：6/6 被抓，且都掉在该掉的那一维 |
| **零重依赖** | 运行只依赖 PyYAML；99 项 pytest 约 58s；另附网页自测台（纯标准库 HTTP） |

## 快速开始

```bash
pip install -r requirements.txt          # 只有一个依赖：PyYAML

python scripts/build_kb.py               # 拆解 wiki 语料 → 结构化知识库
python scripts/gen_cases.py              # 生成 143 条评测用例
python -m dataagent.cli seed             # 造离线数仓（sqlite，固定种子）

python -m dataagent.cli ask "最近7天播放量是多少"
python -m dataagent.cli analyze "2026-09-04 到 2026-09-10 播放量为什么降了"
python -m dataagent.cli govern --sql "SELECT * FROM dws_video_daily"

python -m dataagent.cli eval             # 跑评测，报告写入 docs/reports/
python -m dataagent.cli mutate           # 变异测试：验证评测真的看得见缺陷
python -m dataagent.cli studio           # 本地网页自测台（浏览器里点着测）
```

> Windows 上如果 `python -m dataagent.cli` 找不到包，设置 `PYTHONPATH=src`，或直接 `pip install -e .`。
> 全部命令也可以从 `python -m dataagent.cli selftest` 一键重算，用来核对文档里的数字有没有过期。

## 三个 Agent 的真实输出

以下均为仓库实际运行输出（数仓固定种子，任何人复跑结果一致）。

### ① 数据智能问答 —— 给数，也给口径和证据

```
$ python -m dataagent.cli ask "最近7天播放量是多少"
播放量在最近 7 天（2026-09-18 至 2026-09-24）为 234,195,130 次。
口径：统计周期内视频被播放的次数，每一次起播计 1 次，同一用户重复播放重复计数
（sum(play_cnt)，来源表 dws_video_daily，口径负责人 数据平台-消费数据组）。
```

**口径分不清时反问而不是猜** —— 这是本产品最重要的一条行为。猜错口径会一路污染到结论，而且没人会发现：

```
$ python -m dataagent.cli ask "留存率是多少"
需要先确认口径：「留存率是多少」同时命中 次日留存率 与 7日留存率，
两者口径不同，需要先确认。可选：次日留存率 / 7日留存率
```

越权与敏感问法一律拦截：

```
$ python -m dataagent.cli ask "帮我导出所有用户的手机号"
这个问题涉及个体明细或敏感字段，数据平台侧不直接提供，请走数据权限申请流程后再查询。
```

### ② 自动化数据分析 —— 问「为什么」，按贡献度归因

```
$ python -m dataagent.cli analyze "2026-09-04 到 2026-09-10 播放量为什么降了"
播放量在 2026-09-04 至 2026-09-10 为 229,315,091 次，
较等长基线段（2026-08-28 至 2026-09-03）-0.7%。整体波动在 1% 以内，但维度内部仍有分化：
变化主要来自 category 维度：category=游戏 变化 -2,853,320（贡献 +166.2%），
category=生活 变化 +536,429（贡献 -31.2%）。
按 platform 拆：platform=android 变化 -1,217,493（贡献 +70.9%）。
```

归因链路是：**定指标 → 取当前值 → 取等长基期 → 稳健 z-score 异常检测（中位数 + MAD）→ 维度贡献度分解 → 说人话**。
贡献度分解是把 delta 拆到每个维度值上，**按 |delta| 排序**，不是「哪个维度值最大」——最大的维度值可能根本没变化。

数仓里**故意注入并登记了两个异常**（游戏分区 −45%、PC 端 DAU +38%），所以「归因归对了没有」有客观标准答案，不靠人看着像。

### ③ 数据治理助手 —— 把规范变成可执行检查

```
$ python -m dataagent.cli govern --sql "SELECT * FROM dws_video_daily"
共命中 2 条（P0 1 / P1 1 / P2 0）：
- [P0] G01 分区过滤缺失：查询了 dws_video_daily，但 where 中没有 date 条件；
  建议：在 where 中补充 date 范围条件（责任组 数据平台-治理组）
- [P1] G02 禁止 SELECT *：select 列表中出现 *；
  建议：显式列出所需字段（责任组 数据平台-治理组）
```

每条命中都带 **规则号 + 级别 + 证据 + 修复建议 + 责任组**。规则是**数据驱动**的：10 条规则（G01~G10）写在 wiki 语料里，代码只实现「怎么判」——加规则改语料，不改代码。

## 架构

```
                     data/raw/*.md（非结构化 wiki 语料：指标词典 / 模型规范 / 治理规则）
                              │  build.py：分块 → 字段抽取 → 归一 → 一致性校验 → 知识拆解
                              ▼
              ┌────────────────────────────────┐
              │  知识库 data/built/*.yaml        │
              │  32 指标 / 6 模型 / 10 规则       │
              │  148 知识块 / 12 对易混指标       │
              └────────────────────────────────┘
                              │  index.py：检索（exact / in_query / query_in / ngram）+ 口径消歧
                              ▼
   用户问题 ──→ nlu.py（时间/维度/筛选解析）──→ Planner（确定性规划器）
                              │
                              ▼
                 loop.py 通用 Agent 循环（步数预算 + 全量 trace）
                    │  tools.py：search_metric / read_metric / query / attribute / check_sql ...
                    ▼
              warehouse/（sqlite 离线数仓；查询编译带安全边界）
                    │
                    ▼
        回答 = 数值 + 口径定义 + 计算方式 + 来源表 + 负责人 + 证据块 id

   ───────────────  评测（离线旁路）  ───────────────
   eval/cases.py（143 条用例） × eval/oracle.py（独立期望值：自写 SQL + 自写口径解析）
        → eval/metrics.py（五维判分） → eval/harness.py → eval/report.py（md/html/json）
        → eval/mutants.py（6 个变异体：运行期注入缺陷，验证评测灵敏度）
```

三个 Agent（`qa.py` / `insight.py` / `governance.py`）共用同一个通用循环，区别只在规划器。**规划器与循环解耦**：现在是确定性规则规划器，换成 LLM 规划器时，循环、预算、trace、评测都不用动，可以直接做「规则 vs 模型」的对照评测。

`studio.py` 提供本地网页自测台（纯标准库 HTTP，不重写任何逻辑，只把 CLI 后面的同一批函数包了层网页），页面数字与命令行必然一致，有差分测试盯着。

## 知识库：非结构化语料 → 结构化条目 → 可检索索引

设计立场：**知识库不是一份文档，是一份可以被程序校验、被检索、被引用的结构化数据。**

几条关键设计（细节见 [`docs/知识库构建说明.md`](docs/知识库构建说明.md)）：

- **原始语料是唯一真相源**。`data/built/*.yaml` 必须能从语料逐字节重建（排序 + 固定序列化），`meta.yaml` 记录语料 sha256，护栏测试盯着产物新鲜度——改了语料忘了重建，测试直接红。
- **解析失败要炸，不要兜底**。口径解析不出来比解析错更危险——错口径会静默污染所有回答。构建期有 10 项硬校验，其中最值钱的两条是「指标引用的表必须已注册」「指标依赖的字段必须在表的字段清单里」，把知识库自相矛盾从运行期偶发错误变成构建期必然失败。
- **一个指标拆成多个原子 chunk**（定义 / 公式 / 维度 / 口径注意 / 易混），回答引用的是 chunk id（如 `play_cnt::formula`）而不是整篇文档，「证据」才能对得上具体一句话。
- **易混关系当无向用**。wiki 里易混指标是单向写的，检索时双向生效（12 对），否则「从 B 查 A」会漏掉消歧。
- **子串包含 ≠ 口径冲突**。「人均播放时长」命中时「播放时长」必然也命中，这不是两个口径打架（问得越具体不该越被反问）；但用户只打了「播放」这种片段时，几个口径是真分不开，必须反问。两种情形分开处理。
- **澄清策略**：第二名得分 ≥ 0.80 × 第一名 → 反问，列出可选口径，不给数字；最高分低于下限 → 明确告知「指标平台未注册」。

## 评测体系

这是仓库花力气最多的部分。它回答两个问题：**凭什么说这个 Agent 好用？凭什么相信这个评测本身没在骗人？**（完整方法论见 [`docs/评测体系设计.md`](docs/评测体系设计.md)）

### 143 条用例 × 五个维度

| 维度 | 权重 | 回答什么问题 |
|---|---|---|
| 问答准确率 `accuracy` | 0.35 | 指标选对了吗？数和独立 Oracle 一致吗？治理规则 F1 如何？ |
| 数据推理有效性 `reasoning` | 0.25 | SQL 真的用了口径要求的字段吗？归因主因找对了吗？ |
| 场景适配度 `adaptation` | 0.20 | 该答的答了吗？该反问的反问了吗？该拒的拒了吗？ |
| 响应效率 `efficiency` | 0.10 | 在延迟（2000ms）与步数预算内收敛了吗？ |
| 用户体验 `experience` | 0.10 | 有没有带口径、带证据、带可读结论？ |

用例分布：qa 95 条（基础 64 / 结构化 8 / 消歧 13 / 安全边界 10）· insight 20 条 · govern_sql 21 条 · govern_table 7 条。其中 **23 条是「不该给答案」的用例**（必须反问或必须拒绝）——这类用例最容易被忽略，但它们是「不编数字」这条产品原则唯一的验证手段。

离线基线（143 条全量，0 次模型调用）综合得分 **1.0000**。

### ⚠️ 关于这个满分，必须说清楚

**1.0000 不是能力上限，而是回归基线。** 用例和实现是对着长出来的，一个只会给满分的评测体系等于没有评测。真正说明「评测有没有牙齿」的是变异测试：

### 变异测试：注入 6 类真实退化，看评测能不能看见

| 变异体 | 注入的缺陷 | 结果 | 掉分维度（Δ） |
|---|---|---|---|
| M1-no-clarify | 去掉口径消歧，多候选直接选第一个 | 被抓 | accuracy −0.462 · reasoning −0.462 · adaptation −0.462 · experience −0.231 |
| M2-ignore-range | 时间解析忽略显式区间，一律按最近 7 天 | 被抓 | accuracy −0.273 · reasoning −0.028 |
| M3-disable-G01 | 治理检查漏掉 G01（分区过滤） | 被抓 | accuracy −0.030 · reasoning −0.035 |
| M4-attribution-unsorted | 归因按「变化最小」排序，主因被埋掉 | 被抓 | reasoning −0.028 |
| M5-no-context | 回答只给数字，不带口径与证据 | 被抓 | experience −0.252 |
| M6-distinct-as-additive | 去重指标（活跃UP主数）被当成可加指标求和 | 被抓 | accuracy −0.007 |

**6/6 全部被抓，且都掉在该掉的那一维上**——M4 只掉 reasoning、M5 只掉 experience，说明五个维度确实在测五件不同的事，没有串味。「必须掉在预期维度」本身也被做成了断言（`tests/test_mutants.py`）。M3/M6 掉分幅度小是因为只被个位数用例覆盖，这是评测的真实弱点，写在局限里，不藏。

### 期望值不复用被测代码

评测恒绿的经典成因是「用被测函数算期望值」——实现错了期望值跟着错。本项目：

- 时间区间的期望是**手写死值**，不调 `nlu.parse_time` 反推；
- 数值期望由**独立 Oracle** 计算：它自己解析口径文本、自己写裸 SQL 问 sqlite，完全不走被测的查询编译路径；Oracle 本身再用 4 条**人工手写 SQL 锚点**反向验证；
- 治理用例的期望规则集合按 wiki 规则文本**人工标注**。

## 工程设计原则

这些约束同时是产品行为的一部分：

- **Agent 循环有步数预算**（问答 6 步 / 分析 8 步 / 治理 4 步），跑满预算就停下来说明卡在哪，不无限重试；每一步（工具名 + 参数 + 观察结果）都留 trace，可被评测读取、可被复盘。
- **查询执行有安全边界**：只允许 SELECT；表名必须已注册；列名必须在表的字段清单里；筛选值一律参数绑定；查明细层（dwd/dws）必须带日期区间。
- **去重指标跨维度不可加**：`活跃UP主数` 按分区拆开后不能相加，代码显式返回「不可加」而不是硬算一个数；分母为 0 的比率返回「不可计算」。
- **「今天」取自数仓最大日期，不读系统时间**：否则同一份代码在不同日期跑出不同数字，README 里每个数字都不可复现。

## 诚实的局限

1. **离线基线 1.0000 是回归基线，不是产品能力上限。** 用例与实现对着长出来；真正说明评测有效的是变异测试 6/6。
2. **没有接真实大模型。** 规划器是确定性规则。这是刻意选择——时间区间和口径这类东西让模型自由发挥，错了不会有痕迹；仓库预留了「规划器与循环解耦」的接口，换成 LLM 规划器即可做对照评测，**但没有做过，所以不给数字**。
3. **数仓是自造的模拟数据**，不是真实生产数据；insight 用例的标准答案是注入的异常，真实业务里的异常往往没有这么干净的单一主因。
4. **治理规则判的是 SQL 文本特征**（正则 + 函数调用识别），不是真正的 SQL 解析器，复杂嵌套 SQL、子查询别名遮蔽会漏判。
5. **「用户体验」维是结构化判分**（有没有带口径、带证据、带结论），不是真实用户调研，不能当成用户满意度或 NPS。
6. **归因只做单维度拆解**，没有多维度交叉归因，也没有辛普森悖论检查。
7. **没有统计显著性**：143 条用例单次全量跑，没有重复采样，单次读数就是单次读数。
